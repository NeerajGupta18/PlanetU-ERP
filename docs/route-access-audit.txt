Route access audit: who can read what by id

Every API route that takes a student, employee or institute id, and how it is protected.

Three protections apply everywhere:
- Institute wall. Every signed-in request runs in one database transaction scoped to the institute in the signed
  session, with forced row-level security. An id from another institute simply finds nothing (404).
- Role wall. Each route group checks the role: /api/student (student, parent), /api/parent (parent),
  /api/employee (employee), /api/admin (institute admin, or staff with a role granting that area),
  /api/super-admin (platform owner), /api/assistants (admin, staff role or class teacher).
- A bad id format answers 404 before any query runs (uuidParam).

STUDENT AND PARENT ROUTES (/api/student/...)
These take no student id at all. The student comes from the session. For a parent it comes from middleware/parent.js:
the chosen child must be one of that parent's parent_links rows, otherwise the answer is 403 with no data.

WHAT THE AUDIT FOUND AND FIXED IN 12A
1. Demo data (the bug reported). The seed linked PAR001 to the first two students of each institute, who belong to
   different families. The server was doing what the links said. Fixed in the seed.
2. Wrong child choice was quietly swapped. A parent's chosen-child cookie naming someone else's child was answered with
   their first child and a 200. No other child's data leaked, but it is now a plain 403 with no data.
3. Chosen-child cookie outlived the session. Sign-out and sign-in now clear it. The browser's sign-out also drops all
   data held in memory.
4. API answers could be stored by the browser. All /api answers now say no-store, so a shared phone cannot show them again.
5. "Invite all parents" linked a child to any account with the same guardian email, without the office looking at that
   family. A typing mistake in an email could have joined two families. It now lists that student under skipped, and the
   office links brothers and sisters from the student's record.
6. Every staff role could read the full student record. A librarian or gate guard could open a student's address, phone,
   date of birth, blood group, guardian details, parent logins and ID card through the lookup list. They now get only
   what a picker needs.

LEFT AS THEY ARE, FOR NEERAJ TO DECIDE
- Staff with the admissions, students, certificates or placement area can open any uploaded file in the institute,
  because those desks handle applicants' and students' documents. Narrowing this means tagging each file with its
  owner, which is a migration, so it is reported and not changed here.
